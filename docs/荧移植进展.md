## 一、最大的一个发现：Terran 女性与 Argon 女性共用同一个 component

```
character_terran_female_cau_base_01_macro:
    <component ref="character_argon_female_01" />
```

Terran 女性的 macro 引用的就是 Argon 女性的那个共享 component —— 同一套
91 骨 Biped、同一批 1100+ 条动画、同一套 look-at。

**后果**：
- 骨架侧**零改动**，host 模板（`char_arg_f_dyn_blend_head` /
  `char_arg_f_sweater_leggings_civ_01`）原样复用；
- 但资产的**归属目录**改到了 `assets/characters/terran/lumine/`，与目标种族一致。

### 但"引用同一个 component"不等于"可以照搬替换策略"

艾梅莉埃改的是 **charactergroups 外观池**（把 Argon 女性的池整池换成自己那一
条 macro）。对 Terran **行不通**：

```
character_terran_female_cau_civilian_01_macro
    ref="character_terran_female_cau_base_01_macro"     ← 继承 identification/facemods
    <models>                                            ← 但自己重写了整个 models
      <model type="torso" ref=".../char_ter_f_crew_uniform_01" />
```

**每一个派生 macro 都重写自己的 `<models>`**，把 base 的模型盖掉。所以：

- 改 base macro 的 models → 无效；
- 改外观池 → 能覆盖普通 NPC，但**漏掉所有剧情/任务 NPC**（它们由脚本直接
  指定 macro，不经过池）。

**第一版采用的做法**（今天的 `--mode replace`）：逐个替换这 **45 个** macro 的
`<models>` 块（只动 models，`identification` / `facemods` / `bonemods` 原样保留）。
副作用是好的：

- 池仍然挑选不同的 macro，**NPC 的身份（名字、背景、职称、语音）保持多样**，
  只有身体换了；整池替换会把所有 Terran 女性塌缩成同一个 macro；
- 剧情 NPC 一并覆盖。

**后来补上的默认形态**（今天的 `--mode add`）反过来利用"池"这一层：新增一条
macro 并往池里追加一行，**原版一个不动**，所以她只是随机出现的其中一个，
剧情 NPC 保持原版。两种形态的取舍、覆盖范围与用法见 **§八** —— 这一节下面记录的
仍是第一版（replace）的工程过程。

### "哪些 macro 算 Terran 女性"必须按数据判，不能按名字判

名字极具误导性，两个方向都会错：

| macro | 名字看起来 | 实际 |
|---|---|---|
| `character_yaki_female_cau_base_01_macro` | Yaki 女性 | `race="argon"` ✗ |
| `character_yaki_female_plot_yaki_civilian_macro` | Yaki 女性 | `race="terran"` ✓ |
| `character_player_custom_f_terran_cau_macro` | Terran 女性 | `faction="player"` **是玩家自己** ✗ |
| `character_scenario_combat_ter_gunner_macro` | Terran 剧情 | torso 是 `char_ter_**m**_pilot_suit_01`，男性 ✗ |
| `character_scenario_combat_ter_marine_macro` | 名字里没有性别 | 靠 `ref` 才是女性 ✓ |

判据 = **沿 `ref` 链解析出的有效 `race="terran"` + `female="true"` + 非
`faction="player"`**。

还有一条兜底：两个外交官 macro
（`character_ter_f_diplomat_01_macro` / `character_pio_f_diplomat_01_macro`）
`ref` 的是 **Argon** 的 helper macro，所以有效 race 是 argon —— 但
`terran.factiondiplomat.female` / `pioneers.factiondiplomat.female` 两个池
选的就是它们，玩家见到时就是 Terran 势力成员。

**兜底判据必须是"是否被 terran/pioneers 女性池选中"，不是"是否穿 terran 制服"**：
后者会把 `character_yki_f_diplomat_01_macro`（Yaki 外交官，恰好发了同一套
制服）也拉进来，把一个和 Terran 毫无关系的 Yaki 槽位换成荧。决定权在**谁选它**，
不在它穿什么。

`tools/find_terran_female_macros.py` 输出 45 个，并打印每一个的入选理由，
防止这条规则悄悄扩张。

## 二、源侧（荧 PMX）与艾梅莉埃的差异

| 项 | 艾梅莉埃 | 荧 |
|---|---|---|
| 顶点 / 面 / 骨 | 27.5k / 34.9k / 445 | **17.8k / 22.9k / 272** |
| 坐标映射 | `(x,−z,y)` det=+1 | **同**（重量过：眼球/牙/脚尖/胸全在 −Z） |
| 绕序 | 保持 | **同**（PMX 顶点法线 mean dot = +0.985，positive = 1.000） |
| 拟合 scale | 9.625 | **9.7746** |
| 脊柱段数 | 3（下半身/上半身/上半身2） | **4**（多一个 `上半身3`） |
| 腿骨 | D 骨 | **同**（权重全在 `左足D`/`左ひざD`/`左足首D`/`左足先EX`） |
| 裙摆链 | 177 根 `Q_*` | 80 根（`Q_0_*`…`Q_7_*`，挂 `下半身`） |
| 飘带链 | — | **38 根**（`左带_*`/`右带_*`，挂 `上半身2`） |
| 贴图 alpha | face/hair/cloth **有**遮罩 | **颜/髪/衣 三张图 alpha 全 255** |
| 双面几何 | 作者手工镜像过 | **没有镜像**（0/22868 面有反向孪生） |

### 2.1 PMX 解析器的一个真 bug（material morph 字段宽度）

`pmx.py` 在读表情段时崩在 `morph 62 (風, type=8)`：

```
material morph = MaterialIndex + CalcMode + diffuse[4] + specular[3] +
                 specularity + ambient[3] + edgeColor[4] + edgeSize +
                 texture[4] + sphere[4] + toon[4]
```

原实现把 `texture/sphere/toon` 读成了 `vec(4)/vec(3)/f32`，**每段少读 16 字节**，
于是从第一个 material morph 起整个文件错位。艾梅莉埃的模型没有 material
morph，所以这个 bug 一直没暴露。

> 教训同 §8.1：**几何段在 morph 段之前，所以前 90% 的解析看起来完全正常**
> —— 顶点数、面数、材质、骨骼全对，只有表情之后的内容是垃圾。

### 2.2 脊柱：4 段源 → 3 段目标，映射必须单调（**这里有第二个真 bug**）

髋关节（`左足D`，y=10.96）以上的实测高度，以及 X4 的目标高度（距髋）：

```
下半身  y=12.10  +1.14  →  Bip01 Spine   +12.38 cm
上半身  y=12.17  +1.21  →  Bip01 Spine1  +25.12 cm
上半身3 y=12.70  +1.74  →  Bip01 Spine2  +38.84 cm
上半身2 y=13.51  +2.55  →  Bip01 Spine2  （共用）
```

MMD 故意把 `下半身`/`上半身` 放在几乎同一高度（同一个腰的两个旋转中心，一个
驱动下半身一个驱动上半身），所以拟合不可能同时匹配两者。重要的是**序列递增**。
**"两个源骨共用同一个目标"是错的 —— 这是实机可见的 bug，由用户发现：**
背后的两条飘带被拉到了头顶以上。

```
Bip01 Spine2   src z = 119.0   dst z = 132.9   位移 +13.9 cm
```

`src` 119.0 对应的是 **`上半身3`**（y=12.70），不是 `上半身2`（y=13.51）。
原因：一个 X4 骨只保留**一条** `(src, dst, R)` 记录，而两个源骨写同一个目标时
**谁赢取决于字典遍历顺序**。`上半身3` 赢了，于是 `Bip01 Spine2` 的源位置整体
下移 13.9 cm，所有绑在 Spine2 上的顶点被**向上平移 13.9 cm** —— 而两条飘带的
整条 19 节骨链（`左带_*`/`右带_*`）正是折叠到 Spine2 的。

**修法**：`上半身3` 不再有独立条目，按常规折叠规则落到它的父骨 `上半身`
（= `Bip01 Spine1`）。于是每个 X4 骨恰好有一个直接驱动者：

```
Bip01 Spine  ← 下半身
Bip01 Spine1 ← 上半身 + 上半身3（折叠）
Bip01 Spine2 ← 上半身2
```

新增 `_assert_unique_targets()`：任何两个源骨指向同一目标就直接报错退出。
修复效果：

| | 修复前 | 修复后 |
|---|---|---|
| Spine2 源位置 | 119.0 cm | ~132 cm |
| Spine2 位移 | +13.9 cm | 约 +6 cm |
| Spine2 顶点平均位移 | 13.8 cm | **8.7 cm** |
| 飘带 z 范围 | [55.9, **163.9**] | [51.6, **156.5**] |
| 参照 | Head z=161.4（飘带高过头） | Neck z=153.6（回到颈肩） |

> 教训与 §3.1 的 `dict.get` 默认值是同一类：**一个静默的、由遍历顺序决定的
> 选择点**。它在顶点数、bbox、骨架比对里全都看不出来，只有几何自己会说话。

`腰`（y=11.41）**刻意不映射**：它是半标准骨的过路骨，自身没有皮肤权重，
映射它等于在同一段 12 cm 的脊柱里塞进第四个驱动者。

## 三、四个只有做对才能过的地方

### 3.1 横向阻尼：两套骨架的腿"朝向相反"，不只是"站姿宽窄不同"

实测（cm，源侧为拟合后、目标为 X4 绑定姿态）：

```
          源               X4 Biped
髋     +9.15    →      +11.61   (Thigh)
膝     +7.58    →      +14.81   (Calf)
踝     +5.84    →      +17.70   (Foot)
```

源模型的腿**向内收**（踝间距 11.7 cm），X4 的绑定姿态**向外撇**（踝间距
35.4 cm）。逐骨对齐于是把整条腿甩出去：

```
脚+趾几何宽度：源 23.0 cm  →  重定向后 46.7 cm
```

**修法**：只保留一部分**横向**位移（纵向不动，腿长与落地不受影响）：

```
Thigh ×0.60   Calf ×0.30   Foot/Toe ×0.20   →   脚部宽度 27.7 cm
```

代价是脚部几何不再正落在 `Bip01 L Foot` 上，动画横向摆腿时会略偏。对一个
NPC 来说，藏起来的几厘米胜过长裙侧面戳出来的腿。

> 与艾梅莉埃的 0.30/0.18/0.12 数值不同：那个模型的踝间距只有 6 cm，这个模型
> 的**髋间距本来就与 X4 吻合**（23.1 vs 23.2），错的只有"收/撇"的方向。

> 旋转与位移必须读同一组目标位置。`retarget_core._pair_axis.target_dir()`
> 已经走 `adapter.adjust_target()`（§8.5 的修复），所以改阻尼时两者同步，
> 膝盖不会被撕开。

### 3.2 单面几何 + 双面材质：必须自己造背面，而且背面要有自己的顶点

```
diag_double_sided.py: 22868 面中，有反向孪生面的：0
PMX 材质 flag bit0（双面）：20/20 全部置位
```

MMD 靠渲染器实时双面，X4 剔除背面。所以薄片（发片、衣、裙、飘带、睫毛、
贴花）必须自己补背面层。

**第一次做错了**：背面复用正面的顶点、只反转索引。看起来是免费的（顶点数不变、
只多一倍三角形），但它**毁掉法线** —— Blender 的顶点法线是"所有相邻面的平均"，
一个面和它的反向孪生正好抵消，平均后趋近零向量，归一化后每个顶点指向随机
方向；渲染出来是一片片惨白的碎条，**而且导出器写的 `loop.normal` 就是这些坏
法线**。

**修法**：背面层复制自己的顶点。代价是薄片材质的顶点各多一份，换来的是
背面由自己的绕序算出朝外的法线。

> X4 确实有 `blendmode="TWOSIDED"`（vanilla 有一件角色斗篷用它），但那是渲染
> 状态的承诺，离线无法验证；几何是事实。

### 3.3 导出器硬编码 shader 和 blendmode —— 前一个项目的 alpha 从未生效

`X4CharacterConverter/package_export.py:build_material_library()`：

```python
"shader": "p1_character",
"blendmode": "NONE",
```

**无论 Blender 材质上挂了什么 `x4cc_shader` / `x4cc_blendmode` 都写死这两个值。**

核对艾梅莉埃的成品：18 个材质**全部** `p1_character` + `NONE`，尽管它的代码
设了 `ALPHA1` —— 也就是说它的黑丝从未真正透明过。

**修法**：`make_mod.py` 本来就要重写 `material_library.xml`（修贴图路径占位
符），在那里按 manifest 覆盖 shader/blendmode；manifest 里查不到的材质**直接
报错**，不允许静默退回默认值。

最终：
```
hair                     p1_hair       NONE
skin / elem              p1_character  ALPHA1
其余 16 个                p1_character  NONE
```

### 3.4 重合层：一个丢掉、一个推开

```
hairspec (髪+, sp.png)  1682 顶点，100% 落在 hair 的 1 mm 内（中位 0.00 mm），98% 透明
elem     (元素+, 元素1)  229 顶点，100% 落在 cloth 的 1 mm 内（中位 0.00 mm），88% 透明
```

两个都是**完全重合的叠加层**。X4 的深度缓冲里同深度必然打架（艾梅莉埃的
"黑丝频闪"就是这个）。

- `hairspec` **丢弃**：98% 透明的镜面叠加层，删掉只损失一点头发高光。
  这个决定后来被证明远不止"少一点高光"：导出器把每个材质都写成
  `blendmode="NONE"`（不透明，见 §3.3），而 `hairspec` 与 `hair` 的顶点
  100% 重合、覆盖 2073 个面 —— 留着它，X4 就会用一层**不透明的近黑色**
  把整个头发盖住，**金发直接变黑发**。丢弃它是必需的，不是优化；
- `elem` **保留**：它是胸口的元素徽记，是角色特征。沿源顶点法线**外推 5 mm**
  （只要旋转、不缩放不平移），两层不再共享深度值。

> `肌.png` 的 alpha 是**二值**的（88.1% 恰为 0、11.7% 恰为 255，几乎没有中间
> 值），所以 `skin` 用 alpha test（`ALPHA1`）而不是混合，边缘不会糊。
> `元素1.png` 同理。

### 3.5 预览渲染器本身会骗人：两处必须同步/补齐的东西

这一轮最后花在"为什么预览图里头发是黄黑条纹"上。**结论是预览错了，不是 mod 错了**，
但错法值得记下来，因为两次都差点被当成真 bug：

**(a) 诊断脚本必须和构建管线共用同一份配置。**
`render_textured.py` 直接读源 PMX，把**所有**材质都渲染出来 —— 包括构建阶段已经
丢掉的 `hairspec`。而 `hairspec` 是贴在头发上的近黑色层，软渲染器不做 alpha 混合，
于是把它画成实心黑，头发就成了黑条纹。

定位方式是给渲染器加一个**逐像素材质 ID 缓冲**，然后问"刘海区域最后是哪个材质写的"：

```
刘海区里变暗的像素: 104419
  hairspec  104255  (99.8%)
  eyelash      164  (0.2%)
```

修法是让它 import 构建脚本用的同一份 `DROP_STEMS`。
**一个不共享管线配置的诊断脚本，比没有诊断更糟** —— 它会指着正确的产物说它是坏的。

**(b) DDS 必须带完整 mip 链。**
`bc_encode.py` 原来硬写 `dwMipMapCount = 1`。核对 vanilla 的角色贴图：

```
char_ter_f_afr_blend_head_01_diffhq   2048x2048  mipCount=12
char_ter_f_afr_blend_head_01_diffhq-small  256x256  mipCount=9
```

vanilla **每一张都带完整链**。没有 mip，GPU 只能点采样这些密集的发丝/织纹图集，
于是在任何"一个纹素小于一个像素"的距离上走样成莫尔纹，而且 NPC 在动，**它会爬**。
已给 `bc_encode.py` 补上 mip 金字塔（BOX 降采样、`DDSD_MIPMAPCOUNT` +
`DDSCAPS_COMPLEX|DDSCAPS_MIPMAP`），29 张贴图现在都是 11 级。
`verify_mod.py` 增加了这条检查，防止回归。

> 自检也顺手修了：它原来断言"文件里只有 level 0"，加了 mip 后自然失败。
> 现在改成验证 mip 级数、`DDSD_MIPMAPCOUNT` 标志和总字节数。

### 3.6 贴图透明区的颜色渗漏（实机可见）

`肌.png` 有 **88% 的像素 alpha=0，且这些透明像素的 RGB 是纯黑**。
mip 生成是无差别平均颜色的：落在遮罩边界上的、第 2 级的纹素会是"肤色 + 黑"的混合，
于是采样到边界附近的 UV 读出来就是深灰；而它同时平均出来的 **alpha 落在 0.5 之上**，
引擎的 alpha test **也剔不掉它**。游戏里表现为每条遮罩边缘上的深色斑点。

**修法**：`prepare_textures_lumine.bleed_colors()` —— 在**生成 mip 之前**把不透明像素的
颜色向透明区扩张 12 圈。这样每个 mip 级别的 RGB 都是有意义的肤色，而 alpha 仍然
由遮罩决定。这是标准做法（alpha bleeding / dilation），必须在建 mip 之前做。

量化效果（软渲染，全身边界框，亮度 < 110 记作暗）：

| | 暗像素 |
|---|---|
| 不做 alpha test | 13495（其中 4510 个是纯黑，亮度均值 **6**）|
| 加 alpha test | 8987 |
| 加 alpha test + 颜色扩张 | 8985 |

**alpha test 修掉的那 4510 个纯黑像素，就是"某次迭代后黑条纹消失的一部分"。**
剩下的 8985 个（占身体 3.34%）另有原因，见下。

### 3.7 剩下的深色是模型自己的贴图，不是转换引入的

剩下的暗像素分布与它们的贴图采样：

| 材质 | 暗像素 | 占该材质 | 贴图采样色 |
|---|---|---|---|
| skirt | 5550 | 4.53% | RGB(90,80,76) |
| cloth | 2638 | 3.15% | RGB(99,87,80) |
| skin | 400 | 2.15% | RGB(1,1,1)（遮罩边缘残留）|
| ribbon | 341 | 0.94% | RGB(89,106,128) |
| elem | 28 | 2.03% | RGB(42,40,40) |

把采样点标回贴图（`skirt_dark_atlas.png`）：它们精确覆盖在**贴图上成形的深色部件**上
—— 裙子的内衬/褶皱阴影区、各部件之间那条粗轮廓线。

**同坐标系对照**是最有说服力的判据：把源几何只做全局刚体拟合（不做逐骨转移），
用同一个相机渲染，与成品并排（`cmp_full_sameframe.png`）——**源姿态下的灰块和网纹
比成品多得多**，因为 T-pose 附近有大量内表面朝向相机；X4 的绑定姿态把它们遮住了。

关掉背面剔除再渲一次可以确认剩余的不是背面：剔除后那些像素从亮度 199 掉到 47，
说明**朝向相机的那一层**本身就是深色的 —— 源模型如此，不是重定向的产物。

> 这一轮我在中途走错过两次，都记在这里：一次是把责任推给 `hairspec`（分析脚本拿
> `ib=-1` 当索引，取到了最后一个材质），一次是把它叫做"描边"（贴图上那条线是**部件
> 边界的轮廓**，不是装饰性的描边）。两次都是诊断脚本本身出错 —— 和 §3.5 是同一类教训。

### 3.8 脖子中段的折角（实机可见，已修）

**症状**：脖子上半段相对下半段向左歪，在颈中部形成一个折角。

**定位**（按**源位置**分层，保证前后是同一批顶点 —— 早先按结果 z 分层选到了不同的
顶点集，那些数字不可比）：

| 源 z 层 | 源 x 中心 | 修复前 | 修复后 |
|---|---|---|---|
| 148-151 | −0.01 | **+1.60** | **−0.00** |
| 151-154 | −0.01 | **+0.57** | **−0.00** |
| 154-157 | −0.01 | −0.00 | −0.00 |

**根因**：颈部下段的原始权重是 **`上半身2` 58% + `首` 42%**。在 MMD 里两者由同一套
动画驱动，无所谓；但重定向之后 `上半身2` → `Bip01 Spine2` 带 **9.9° 的拟合旋转**，
而 `首` → `Bip01 Neck` 只有 0.3°。颈部距 Spine2 枢轴约 26 cm，9.9° 在那个半径上
就是 **1.6 cm 的横向扫掠**，而上半段（100% `頭`）纹丝不动 —— 于是颈中折角。

**关键顺序教训**：第一次的修法是在 stage1 里改**最终**权重（`rebind_neck`），
它跑了、移动了 674 个顶点、**折角一点没变**。因为顶点位置是在 `transform()`
**内部**用权重算出来的 —— 等权重被改时几何早就扫过去了。正确做法是在
`transform()` **之前**改**源**权重：`mmd_to_x4.fix_neck_source_weights()`，
把颈部（|x|<7、z 145–157）的 `上半身2` 权重转给 `首`。331 个顶点，折角归零。

> 权重平滑解决不了这个问题（试到 6 轮：1.65 → 2.03 cm）。偏移是"任何在那里带
> Spine2 权重的顶点"的属性，与权重变化是否陡峭无关。

### 3.9 预览渲染器把 alpha 剪裁写在了深度写入之后

用户从第一轮起就说"手臂、胸口、腿上有黑条纹，原本没有"。追了很多轮，最后发现
**问题在预览渲染器，不在 mod**：

```python
sub[hit] = zz[hit]              # 深度写入  ← 用了 alpha test 之前的 hit
...
hit = hit & (av > 0.5)          # alpha test
img[...][hit] = col             # 只有这里用了 test 之后的 hit
```

**被 alpha 剪裁掉的纹素仍然占住了深度缓冲**，于是它们后面的几何（比如腿的另一侧）
填不进来，露出来的是背景色 —— 看上去就是白衣服上的一道道黑条纹。
GPU 是**先测 alpha 再写深度**的，游戏里不会有这个现象。

把深度写入移到 alpha test 之后，手臂、胸口、腿上的条纹**全部消失**。
`肌.png` 有 88% 的 alpha=0，这个模型对这种顺序错误格外敏感。

> 三条教训叠在一起：**诊断脚本必须和被测对象行为一致**。前面 §3.5 的 DROP_STEMS、
> §3.6 的可见性分析、这一节的深度顺序，都是"我的尺子错了，却在量产品"。

### 3.10 贴图上下翻转（实机可见，已修）

**症状**：实机贴图紊乱。

**根因**是一条被两个项目都踩过的坐标约定链：

```
PMX 的 v：0 在图像顶端（向下）
Blender 的 v：0 在图像底端（向上）      -> 差一次 1-v
导出器 addon.py:855：  v_x4 = 1 - v_blender
导入器 addon.py:531：  v_blender = 1 - v_x4    （对称，所以 v_x4 与 Blender 反号）
```

两条合起来：Blender 里存的必须是 `1 - v_pmx`，导出器再翻一次才得到 `v_pmx`。
而 stage1 原来**原样传递** `v_pmx`，于是 Blender 里是上下颠倒的，导出后 X4 拿到
`1 - v_pmx` —— **整张贴图上下翻转**。

> 艾梅莉埃的代码里有一句注释"pass through unchanged: the exporter applies
> `1 - uv.y` itself"。那句话只对了一半：导出器确实会翻，但**它翻的是 Blender 的 v，
> 而 Blender 的 v 和 PMX 的 v 本来就差一次翻转**。少了这一步，翻转就被带进游戏。
>
> 为什么之前没发现：**软渲染用的是源 PMX 的 UV**（不经 Blender），所以预览一直是对的，
> 只有实机才乱。这是本项目第三次栽在"预览与实机走的不是同一条路"上。

**修法**：stage1 存储 `(u, 1 - v)`。验证：

```
源 PMX skin      v [0.0615, 0.9263]
期望存储 1-v      [0.0737, 0.9385]
导入 xac 后       [0.0737, 0.9385]   ✓ 与 Blender 侧一致
```

### 3.11 去掉背面壳：两层同深度必然频闪

§3.2 曾经为了"薄片从背面可见"而**复制一份反向几何**当背面层。它在离线指标上
完全看不出问题（顶点数、bbox、骨架都对），但**两层壳位置完全相同 = 同一深度**，
在游戏里就是一片片闪烁的补丁 —— 与艾梅莉埃"黑丝频闪"是同一个失效模式。

其实游戏早就给了正解：**`blendmode="TWOSIDED"`**（vanilla 有一件角色斗篷
`p1_char_spl_f_cloak_gen_01` 用的正是 `p1_character` + `TWOSIDED`）。
它是渲染状态，不占几何，也不可能和自己打架。

最终材质表：

```
薄片（hair/acc*/cloth/ribbon/skirt/petti/eyelash/brow/eyelid/face2/eyespec/mouth）
        p1_character（hair 用 p1_hair） + TWOSIDED
封闭实体（face/eyewhite/iris/teeth）    p1_character + NONE
实测 alpha 面（skin/elem）              p1_character + ALPHA1
```

顺带的收益是顶点预算：

| 资产 | vanilla | 双面壳版 | 现在 |
|---|---|---|---|
| head | 4693 | 8195（1.75×）| **4813（1.03×）** |
| body | 3601 | 20513（**5.70×**）| **11325（3.15×）** |

body 从贴着 6× 安全线降到 3.15×，mod 体积 3.0 → **2.2 MB**。

### 3.12 **已知问题**：关节处的残余撕裂（尝试过修复，已回退）

**症状**：脚腕处可见断裂/台阶、肩臂之间有缝、手肘处异常。

**先纠正一个错误的度量**。我最初用"边长超过网格中位 6 倍"来判撕裂 —— 那是错的，
它抓到的是这个模型本来就有的长结构边（一条源长 9.3 cm 的边，结果长度也是 9.3 cm，
两端权重还完全相同，根本没被拉伸）。正确的度量是**边长比（结果 / 全局拟合）**：

```
边 40587 条，拉伸比中位 1.000，99% 分位 1.966，最大 6.81
拉伸比 > 2.0 的 394 条：躯干 314、大腿 130、脚踝 28、肩颈 4
```

**根因**：这个 MMD 骨架的 `下半身` 与 `上半身` **只差 0.7 cm**（MMD 把脊柱骨叠在腰上），
而 X4 的 `Bip01 Spine` 与 `Bip01 Spine1` **相差 12.8 cm**。逐骨各对各的目标，就把源里
几乎重合的两组顶点拉开 12.8 cm；蒙皮在两者之间混合，于是**每一条跨越它们的边都被撕裂**。
判据很直接：394 条里有相当一部分**两端的主导骨是同一根**（`Spine`/`Spine` 72 条）——
同一根骨的变换是刚体，不可能改变距离，所以拉伸只可能来自"位移不同的骨之间的混合"。

**权重平滑解决不了**：4 / 10 / 20 / 40 轮的结果**完全相同**（313 条，用粗度量）。
两个相差 12.8 cm 的坐标系做混合，无论混合得多平缓都会撕。

**试过的修法**：`mmd_to_x4.blend_chain_offsets()` —— 给一条链一个共享位移，与
`retarget_core` 里已有的 `_harmonise_head_neck`（头颈）和 `_feet_share_one_offset`
（脚）同一思路。

| 链 | 位移跨度 | 数值结果 |
|---|---|---|
| Spine / Spine1 / Spine2 | 12.6 cm | 躯干撕裂 314 → 134 |
| L/R Thigh / Calf / Foot / Toe0 | 14.4 cm | 大腿 130 → **1**，脚踝 28 → **0** |
| L/R Clavicle / UpperArm / Forearm / Hand | **18.8 cm** | 手渲染成**张开的爪子** |

**已回退，全部禁用。** 用户实测反馈：数值上撕裂确实减少了，但**手臂和脚腕出现了新的
弯折**，比它修掉的缝隙更显眼。手臂链（跨度 18.8 cm，主要是手距 X4 目标 15.4 cm）
尤其不可接受 —— 平均后每根骨偏出近 10 cm，手的形状被拉成爪子。

**当前状态**：只保留 `fix_neck_source_weights`（脖子中段折角，见 §3.8，那个是局部且
已验证归零）。脊柱与四肢的位移协调**全部禁用**，函数定义保留以便复现。

**代价的取舍**：撕裂的根源是"源骨架与 X4 骨架的脊柱/腿长比例不同"，这是**换骨架的
固有代价**。真正干净的做法是改骨架比例，但那会破坏"骨架必须与 vanilla 逐字节相同"
这条硬规则。目前的取舍是：**保留骨骼的精确对齐，接受关节处的残余缝隙**。

### 3.13 胸口黑带频闪：衣服和皮肤完全重合（**已修，保留**）

`diag_overlays` 量到 `cloth ↔ skin` 有 **3331 对顶点距离小于 4 mm，最小 0.00 mm** ——
上衣就是贴在身体表面上的。两个面同深度必然 z-fight，实机就是胸口那条闪烁的黑带。

修法和 `elem` 一样：**沿顶点法线把衣服外推 2 mm**。
`build_lumine_x4.py:CLOTH_OFFSET = 0.2`。NPC 距离上 2 mm 看不出来，但足够让两个面
不再共享深度值。

> **争同一批池**：同一条 `<select>` 列表里谁在最后、谁加载得晚，谁就是那个人；
> 装两个不会崩，但同一个 Argon 女性最终只会是其中一个。想固定看某一个，
> 就只启用对应的那一个扩展。

## 八、两种形态 + 两个种族（`--race` / `--mode`）

本节是后来补的：第一版是「泰伦 · 45 个 macro 逐个替换」，现在 `make_mod.py` 变成
带命令行参数，一次能生成全部形态与种族。

```bash
python tools/make_mod.py --race <terran|argon> --mode <add|replace> [--weight N]
```

| 参数 | 取值 | 说明 |
|---|---|---|
| `--race` | `terran`（默认）/ `argon` | 进谁的池。两族**共用 `character_argon_female_01`**，网格完全一样，所以只是 base macro（决定 `race` 标记）与目标池不同 |
| `--mode` | `add`（默认）/ `replace` | `add` = 往池里加一个候选；`replace` = 全部替换（含剧情 NPC） |
| `--weight` | 整数，默认 1 | 只在 add 模式生效：每个池里列几条荧。池里原本 3 个候选时，1 条 = 1/4，2 条 = 2/5 |

### 8.1 `--mode add`（默认）：加入外观池

新增一条 macro（`<add sel="/macros">`，`ref` 该种族的 cau base macro，继承
`identification` / `eyepositions` / `facemods`；`props` 置 `none`），再往每个目标池
`<add sel="/characters/character[@name='池名']">` 追加一条 `<select macro=...>`。
**原版 macro 一个不动、池里原有条目一条不删**，所以她只是"随机出现的其中一个"，
其余女性保持自己的脸 / 名字 / 语音。

**覆盖范围（实测）**

```
--race terran : 12 个池 —— terran 与 pioneers 各 6 个
                civilian / manager / marine / pilot / service / factiondiplomat 的 .female
--race argon  :  6 个池 —— argon.civilian(6 候选) / commander(3) / marine(3)
                / pilot(3) / service(3) / factiondiplomat(1) 的 .female
```

池的清单是**从原版 `charactergroups.xml` 发现**的（名字以该种族的池前缀开头 +
`.female`、且自己直接列 macro）；只做路由的池（`argon.trader.female` →
`argon.civilian.female`）不用单独写，它指向的叶子池已经在清单里。

**与 replace 的关键差别**：剧情/任务 NPC 由脚本直接 `ref`，从不经过外观池，
所以 **add 模式下它们保持原版外观**。想让剧情 NPC 也是荧，用 `--mode replace`。

### 8.2 `--mode replace`：全部替换

- 泰伦：读项目内 `work/terran_female_macros.json`（`tools/find_terran_female_macros.py`
  生成）里的 **45 个** macro，逐个 `<replace>` 掉 `<models>`；
- 阿贡：Argon 的派生 macro 继承 base 的 `<models>`，不需要逐个改，改池即可，
  所以 `--race argon` **只做了 add 形态**（代码里的 `argon_female_macros.json`
  清单没有生成，真要用得先生成它，否则 `--race argon --mode replace` 会直接报错退出）；
- 两种形态都覆盖不走外观池的剧情 NPC（replace 是全量覆盖，add 是不覆盖）。

### 8.3 输出目录与发布包

两种形态互不覆盖，各自一个目录；发布包由工作区的 `work/build_release.py`
统一生成，文件名写清配置：

```
work/x4_lumine_terran_add/       -> x4_lumine_mod_terran_add_v1.4.zip
work/x4_lumine_terran_replace/   -> x4_lumine_mod_terran_replace_v1.4.zip
work/x4_lumine_argon_add/        -> x4_lumine_mod_argon_add_v1.4.zip
```

`verify_mod.py` 也带同样的 `--race` / `--mode`，并按模式做不同断言：

- **add**：每个目标池都多了荧、**且原版条目一条不少**、且没有残留 `<replace>`
  （残留会把"多一个选项"悄悄变回"唯一选项"，不盯着剧情 NPC 根本看不出来）；
- **replace**：补丁集完整，且没有池还能选到原版 macro。

## 九、步态修复：走路的"猫步"（v1.4）

### 9.1 症状

实机反馈两句：「走动时是猫步，左脚放到右脚位置，右脚放到左脚位置」；
「坐姿两只脚贴得很近」。静止站着看起来没问题。

### 9.2 先排除掉的（都没问题）

按 skill 的顺序，凡是能"用数据判死"的先判死，避免在错误的方向上改东西：

| 假设 | 判据 | 结果 |
|---|---|---|
| 左右腿骨映射反了 | 写出 `tools/xac_skeleton.py`（不依赖 Blender 读 .xac 骨骼），比对每根腿骨的位置与局部轴 | 与 vanilla **逐项相同**，镜像误差 0.0° |
| 骨架被动过 | `xac.compare_skeletons` | 91/91 逐字节相同 |
| 权重挂到了对侧 | 按主导骨分组统计顶点 x（X4 的 `left_eye_dummy` 在 +X，所以 **+X 是角色左侧**） | 左右各自归位，跨侧权重只有裆部 15 个顶点、权重 <0.05 |
| 源模型本身是内八/交叉 | 在源 PMX 里算"源骨位置 vs 它驱动的顶点中心" | 源侧偏差 **0.69–0.97 cm**，源数据完全健康 |
| 脚骨旋转被跳过导致脚朝向错 | `NO_ROTATE_BONES` 实际跳过的旋转量 | 荧这里是 **0.0°**（大腿 3.5°、小腿 2.3°），跳过无副作用 |

### 9.3 根因：横向阻尼逐级打折，把骨链折向了内侧

`LATERAL_DAMP` 是按骨链给不同折扣的：大腿 0.60、小腿 0.30、脚 0.20。
逐级打折不只是把腿**平移**，它把骨链**折弯**——每一节都比上一节更靠内，
于是关节落在它所驱动的几何内侧：

```
bone            X4 绑定     v1.2 目标     它驱动的几何
Bip01 L Thigh   +11.61      +10.62          +10.76
Bip01 L Calf    +14.81       +9.75           +8.79
Bip01 L Foot    +17.70       +8.21           +8.99
Bip01 L Toe0    +21.50       +9.05           +9.84
```

绑定姿态看着是对的（网格就是按这些目标生成的），但两个后果在动画里才暴露：

1. **两脚间距只有 16.4 cm**（骨）／**18.0 cm**（几何中心），而 vanilla 是
   39.8 cm —— **不到一半**。走一步就把两只脚放到一条线上，正是"猫步"；
   坐下时两脚也自然聚在一起。
2. 脚踝关节落在脚部几何**内侧 7.06 cm**，小腿骨偏离小腿几何 5.06 cm：
   动画绕着错误的支点带这些顶点。

### 9.3b 用户实机反馈定了性：「脚跟脚踝、小腿跟大腿，动作完全不变形，就是猫步」

这句话把范围缩到只剩一个量：**步态宽度**。骨架、父子链、局部坐标系、权重跟随
都没问题（§9.2 已逐项证同），那就是脚落地的横向位置不对——而"猫步"的定义正是
"两只脚落在一条线上"。vanilla 女性走路时两脚相距 **39.8 cm**，阻尼过强的版本
只有 **18.0 cm**，比骨盆（23 cm）还窄，每一步都跨过中线。

### 9.4 修法

第一步（v1.3）只把脚踝推到 14.4 cm（几何 30.5 cm），**仍是 vanilla 的 77%**，
实机看着依旧像猫步——**"没用"**。第二步（v1.4）按"步态宽度要对齐 vanilla"
来定参数，让脚保留几乎全部横向行程：

```python
LATERAL_DAMP = {Thigh: 0.60, Calf: 0.85, Foot: 0.95, Toe0: 0.95}   # 左右同值
```

骨链仍单调外撇（10.62 → 13.72 → 17.11），脚踝落在 17.11 对 vanilla 的 17.70。

### 9.5 修复前后（实测，`tools/measure_legs.py` 直接量新导出的 .xac）

| 指标 | v1.2 | v1.3（不够） | **v1.4** | vanilla |
|---|---|---|---|---|
| 两脚间距（几何中心） | 18.0 cm | 30.5 cm | **35.9 cm** | 39.8 cm |
| 脚趾间距 | 18.0 cm | 32.0 cm | **37.5 cm** | — |
| 脚踝骨 vs 脚部几何 | 7.06 cm | 2.47 cm | **0.28 cm** | — |
| 小腿骨 vs 小腿几何 | 5.06 cm | 0.96 cm | **1.38 cm** | — |
| 大腿骨 vs 大腿几何 | 1.05 cm | 0.41 cm | **1.14 cm** | — |
| 骨链横向单调性 | 折向内（10.62→9.75→8.21） | 外撇（→12.28→14.38） | 外撇（→13.72→17.11） | 外撇 |
| 骨架 / 父子链 / 局部矩阵 | 与 vanilla 相同 | 相同 | **逐值相同**（旋转差 <1e-6 度） | — |

腿外移后仍在裙子内：裙摆最窄的一圈（z 40–50）半宽 **24.3 cm**，宽处 36–42 cm，
而这个模型的腿部几何本来就被裙子遮到 z = 42 以下，可见的只有脚。

### 9.5b 实机确认（v1.4）

「v1.4 可以了」——步态修复在实机通过。

> **但前一轮的"没用"不是参数不够，而是根本没装上。** 游戏
> `extensions/x4_lumine_mod/` 里躺着的是 **9/24 15:40 的 v1.0**
> （`content.xml` 里 `version="100"`，最早那版"全部替换"）：从 v1.2 起的
> 每一步修复都没进过游戏，用户看到的"猫步"是初版的表现。
>
> 我连做二十多轮离线诊断，一次都没检查过"游戏里实际装的是哪一版"——
> 这是本项目最贵的一个流程漏洞，已写进 skill 的验证纪律（§10）：
> **发版之后第一件事是核对游戏 `extensions/<id>/content.xml` 的 version，
> 而不是继续改参数。**

### 9.6 教训

- **"横向阻尼"是两套骨架比例差的对策，但它打折的是骨链形状，不只是位置。**
  逐级递减（0.6/0.3/0.2）会让骨链折弯；同一条腿用接近的折扣才只是"整体平移"。
  判据不是"绑定姿态好不好看"，而是**每根骨与它驱动的几何差多少**——
  这个量在绑定姿态的截图里完全看不出来。
- **两脚间距是个便宜的判据**：vanilla 39.8 cm，做出来 18 cm 就该怀疑了。
- 这一轮又是"先写工具再下结论"救回来的：`xac_skeleton.py`（读 .xac 骨骼）、
  `diag_legs.py`（左右镜像）、`diag_weights.py`（权重侧别）、
  `measure_legs.py`（Blender 侧终极测量）、`measure_foot_axis.py`（脚骨 vs
  脚几何的轴夹角）——前几个把嫌疑逐一排除，后一个给出修复量。
  **其中 `diag_legs.py` 自己先错了两次**（判据写成了 `diag(-1,1,-1)`，
  把反射变成了旋转，于是所有资产都"误差 180°"）。
- **但真正定性的信息来自用户的一句实机描述**："脚跟脚踝、小腿跟大腿，动作
  完全不变形"。这一句把范围从"全身骨骼"缩到"只有一个量不对"，比二十轮离线
  测量都有效。**症状描述里的每个限定词都要当判据用**——"不变形"三个字就
  排掉了蒙皮、父子链、骨轴三大类原因。
- **"猫步"这个词本身就是判据**：它是"两脚落在一条线上"，所以度量它的是
  **两脚间距**，而不是骨骼某处的偏差。我第一轮修完只报了"脚踝偏差从 7 cm
  降到 2.5 cm"，那个指标和猫步根本不是一回事。**先把症状翻译成一个可测的
  量，再去改参数。**
